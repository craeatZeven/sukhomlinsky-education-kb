# 卡片互链层审计（2026-09-21）

## 一、先记一件我搞错、并已回滚的事

我按「**seealso 全库为空**」这个前提去补卡对卡双链。错了两处：

1. **seealso 存的是条目码（A 码），不是卡片 id。** 全库 **399 张卡本来就在用它**
   （A19×61、A4×47、A15×38、A8×33…），是「这张卡还归属于哪些条目」的跨条目引用。
2. **站点就是按条目码渲染它的**：`web/card.html:128`
   `const seeBadges = (c.seealso || []).map(code => KB.entryBadge(code, {kind:"see", cross:true}))`
   —— 塞 sk-id 进去会让徽章渲染失效，还把两套命名空间混在一起。

更糟的是我的脚本是**整块替换** seealso，那会**删掉已有的跨条目引用**（399 张卡的历史数据）。
发现后立即 `git checkout -- cards classification.json` 回滚 + 重建，`validate_all` **ALL OK**，
回滚后复核：seealso 非空 399 张、sk- 开头 0 项。

**为什么我的审计会得出「0 张非空」**：脚本只数了 `- sk-` 开头的项。
→ **判「字段是否为空」要用字段自己的取值空间，不是我假设的格式。**

## 二、卡片互链其实早就有机制（2026-09-16 起）

- **写法**：Markdown 正文里写 `[[sk-XXXX]]`（Obsidian 双链）。
- **渲染**：`web/kb.js:457 KB.linkify` → `<a class="wikilink" href="card.html?id=…">`，
  链接文字自动换成**目标卡的标题**（`card.refs` 构建期算好），`title` 属性里带编号。
  kb.js 的注释写着为什么必须认它：「否则页面上会直接显示方括号」。
- **卡片详情页的链路**：`card.html:191 ${KB.usageHTML(c.usage, c.refs)}`
  → `kb.js:485 usageHTML` → 逐行 `KB.linkify(l, refs)`（第 492/495 行）✅ 接对了。
- **纯文本场景**（标题、摘要、meta 描述、被截断的片段）会把记号洗掉，
  且片段从中间切时会把半截 `[[sk-0026]]` 一并删掉（`kb.js:260-262`）。

## 四、互链密度能不能机械地补？——不能

1598 张里只有 165 张发出链接，看上去「太少」。但：

- `seealso` 是**条目域**（A 码），不是卡片域；
- `[[sk-XXXX]]` 是**内容判断**——「这张卡的场景里真的用得上那张卡」。
  它可以机械生成的只有「同 primary + 同 topics」这类**弱关系**，
  而把 351 条有判断的链接掺进几千条弱关系，等于**把信号稀释成噪声**。

**所以互链密度只能按内容提，是逐卡编辑的活，不是脚本的活。**

## 五、可脚本化的部分（留给下次）

能给编辑的是**候选清单**，不是直接写卡：同一 topics + 同一书源、或引文出自同一小节（locator 的 section 相同）的卡片两两配对，
按「同节 > 同 topics > 同源」排序，一次给人看 20 对，挑真相关的写进「教育场景/应用」。
