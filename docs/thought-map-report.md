## 2. 我改了什么（2 处，都在 `web/style.css`；数据层与 `scripts/` 未动）

### 2.1 规模图的条形整条不可见（严重，已修）

**现象**：`.bar-primary` / `.bar-cross` 的布局宽度完全正确（A19 = 819.45px），但**高度被压成 0px**，
两处视口的截图里一根条都看不到——整张「规模图」实际上只剩数字，图没了。
渲染验证里「读宽度算比例」这一条会完全放过它（宽度确实是对的）。

**根因**：`.bar` 这个类名被两个组件共用，且后出现的一条覆盖了前一条：

- `style.css:259`（思想地图）`.bar { display:block; height:8px; ... }`
- `style.css:391`（覆盖报告的进度条）`.bar { height:100%; background:var(--accent); border-radius:999px; }`

两条同为单类选择器（特异性相同），391 行更靠后 → `height:100%` 胜出；而 `.map-bars` 的高度是 `auto`，
百分比高度无法解析 → 回退成内容高度 → 空 `<span>` = 0px。
同一个覆盖还让 `.bar-cross`（浅色被参见条）失去自己的半透明色，变成与主归属条同色。

**修法**（一行根因修复，不动物理布局）：

```css
 /* Coverage bars */
-.bar { height: 100%; background: var(--accent); border-radius: 999px; transition: width .3s ease; }
+.bar-wrap .bar { height: 100%; background: var(--accent); border-radius: 999px; transition: width .3s ease; }
```

**回归验证**（`local_working_copy/web-audit/check-coverage-bars.mjs`，已验证）：`coverage.html` 里 24 条进度条
仍是 6px 高、圆角 999px、颜色 `rgb(47,107,79)`，`.bar-wrap` 外没有游离的 `.bar`。
全站只有 `clusters.html`（地图条）与 `coverage.html`（进度条）两处用 `.bar`，见 grep 结果。

**修后证据**：

- `verify-map.json` → `checks.barPaint`：23 行的条形高度集合 = `[8]`，命中测试 `{"at":"span.bar.bar-primary","h":8}`
- `shots/map-1280-rows-crop.png` 的像素扫描：主归属条绿色 `rgb(47,107,79)` 出现在 20 段**恰好 8 行高**的横条上
  （更短的两条 A17 38.8px / A20 77.6px 因采样步长漏检，不是没画）

### 2.2 移动端数字被挤到行首（已修）

**现象**：`@media (max-width:680px)` 下 `.map-row` 是三列 `36px 1fr auto`，`.map-bars` 又占了 `2/4`，
网格自动排布把 `.map-num` 丢进了**第一列**（宽 36px），而它的内容有 77px：

```
375 行实测：.map-num 盒 = [16, 52]（宽 36px），内容 scrollWidth = 77px
→ 数字贴着行左边缘渲染（实测文字像素 x 从 16.3 起），而不是设计意图的右对齐
```

**修法**（只改移动端媒体查询）：

```css
 @media (max-width: 680px) {
   .map-row { grid-template-columns: 36px 1fr auto; }
   .map-bars { grid-column: 2 / 4; }
+  /* 数字回到第一行右侧 */
+  .map-num { grid-row: 1; grid-column: 3; }
 }
```

**修后**：390 下 `.map-num` 盒 = `[297.45, 374]`，右边界 374 = 行右边界，内容 77px 完整放下、零截断；
行高从 75~77px 降到 48.5~58.5px（少一行），`map-390-rows-crop.png` 里数字已右对齐、条形正常显示。

## 4. 可读性自评（如实写，不替谁圆）

### 4.1 矩阵 22×22 在 1280 下每格多大？数字看得清吗？

- 每格实测 **48.97 × 48.97 px**（面积 2398px²），矩阵总宽 1136px（含约 30px 行头列），总高 1169px。
- 格内字号 **10px**，最多两位数字（最大 14），单个数字宽约 5~6px、两位约 11px。
  **数字绝对看得清**（10px 字在 49px 格子里留白极大，实测 484 格里没有一次溢出/换行）。
- 但要说句实话：**10px 明显偏小、偏保守**。格子里有 49px 的余量，正文最小字号体系里也还有 12px 一档，
  把 `.mx-cell { font-size: 10px }` 提到 12px 完全放得下（两位数约 13px < 26px，移动端也不会溢出），
  观感会明显更从容。**这是设计取舍，我没有擅自改**，留给你定。

### 4.2 颜色深浅分 4 档够不够分辨？

4 档实测（`color-mix(--accent, transparent)` 合成到页面底色 `rgb(242,240,230)` 之后）：

| 档 | 语义 | 合成后底色 | 相对亮度 | 与前档亮度差 | 格内文字色 | 文字对比度 |
|---|---|---|---|---|---|---|
| `sw-0` | 0（空格） | `rgb(231,230,220)` | 0.7875 | — | `rgb(32,37,31)`（但空格无数字） | 12.45:1 |
| `sw-1` | 少（1~3） | `rgb(199,211,197)` | 0.6264 | 0.161 | `rgb(32,37,31)` | **10.05:1** |
| `sw-2` | 中（4~8） | `rgb(148,176,158)` | 0.3990 | 0.227 | `rgb(32,37,31)` | **6.67:1** |
| `sw-3` | 多（9~14） | `rgb(82,131,106)` | 0.1906 | 0.208 | `rgb(238,242,236)` | **3.85:1** |

- **档与档之间分得开**：相邻档亮度差 0.16 / 0.23 / 0.21，目视是四个清楚的台阶，不是"深浅差不多"。✅
- **0 档与 1 档也不糊**：空格 `rgb(231,230,220)` vs 最低档 `rgb(199,211,197)`，差 0.16 亮度，能看出"这里有值/没值"。✅
- **唯一要提醒的是最暗档的文字对比度 3.85:1**：`sw-3` 用浅色 `--chrome-ink` 写在深绿上，10px 字号属于小字，
  **低于 WCAG AA 对小字的 4.5:1**（只满足大字的 3:1）。落在这一档的是 9~14 这种"最密"的格子——
  恰好是最值得看清的数字。可选的小修法：`sw-3` 的文字改成纯白（算下来约 4.36:1，仍差一点）或把 `sw-3` 的
  `82%` 调深到 ~88%（可过 4.5:1）。**同样属于配色决策，我没动，留给你定。**
- 顺带说明：矩阵容器本身是透明的，我第一版把半透明底色合成到了黑色上，算出来的对比度（1.15~1.33）是错的；
  上面这张表是修正后（合成到页面底色 `rgb(242,240,230)`）的真实值。

### 4.3 新增的两件事（本轮按你的要求给结论）

**角度色带让"分块"看得出来了吗？——看得出来，而且是这次改动里最有效的一笔。**
色带文字 11px、色带高 28.25px，宽度精确等于各角度的列数（5:3:3:9:2，误差 0.00%），
在 `map-matrix.png` 里可以一眼读出「前 5 列是宗旨、接着 3 列是立场……最后 2 列是衡量」；
列头那串裸数字（`1 2 3 4 19 5 6 21 8 …`）为什么第 5 列是 19，现在有了直接答案。
色带文字用 `--soft`（`rgb(97,104,94)` 压在 `rgb(242,240,230)` 上）实测对比度约 4.6:1，11px 下够读。

**分隔线（3px）够不够清楚？——够用，但属于"第二眼"级别的弱信号，不是强分割。**
实测像素：分隔线是 `border-right: 3px solid color(srgb .125 .145 .122 / .2)`，
它以 20% 的墨色**压在该列格子的底色之上**再与底色混合，所以深浅随格子而变：

- 压在 `sw-1` 上 → `rgb(166,175,163)`（比格子底色暗约 33 个灰阶）
- 压在 `sw-2` 上 → `rgb(125,148,133)`
- 压在 `sw-0` 上 → `rgb(191,190,182)`（比格子底色暗约 40 个灰阶）

亮度落差约 0.27，肉眼能看见，且它与隔壁 2px 的页面底色缝一起构成"格—深线—缝—格"的节奏，
块与块之间确实断开。但因为它只有 3px、又是半透明叠色，在缩略图/低分屏上会明显变弱；
**真正让人"看出分块"的仍是顶部色带，分隔线是辅助。** 如果想让分组更硬，可把 `--ink 20%` 提到 30~35%
或改成实色（例如 `var(--line)` 加深版）；现状我认为是够的，不构成缺陷。

### 关于「平均每个条目连 36 条」（唯一一处数据与文案对不上）

`clusters.html` 第 82 行的这句是**手写死的**，不是从 `map.json` 算的。以当前数据：

- 单向（出边）：416 ÷ 22 = **18.9 条/条目**
- 双向（把别人指过来也算"连"）：2 × 416 ÷ 22 = **37.8 条/条目**
- 123 对无向配对 ÷ 22 = 5.6 对/条目

三种口径都不是 36。**同上一条「123 对（53.2%）」「416 条」都是对的**，只有这个均值对不上，
像是上一版数据（若边数是 396，则 2×396/22 = 36.0）残留下来的。
因为它属于"哪个口径算平均值"的语义选择，我**没有替你改**——建议要么删掉这个均值，要么改成与数据同源的写法：

```js
'一共 ' + map.edges + ' 条、平均每个条目连 ' + (map.edges * 2 / map.entries.length).toFixed(0) + ' 条'
```
